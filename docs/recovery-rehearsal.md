# Demo recovery rehearsal

These operator scripts implement a **manual cold backup**, with a brief maintenance window. They do not schedule backups or guarantee a daily RPO. Run them only on the authorized Docker host. The root-only backup includes credentials and container configuration; never publish it or place it in a web root. Use a separately authorized encrypted off-host copy for host-loss recovery.

1. Finish active runs, ingestion and exports. Verify no deployment is running. Choose a new directory under `/data/semibrain/backups`.
2. Run `python3 scripts/ops/cold_recovery.py --output /data/semibrain/backups/<new-name> --maintenance-confirmed`. It closes ingress, stops workers, rechecks outstanding work, fingerprints authoritative Mongo collections and the synthetic Postgres tables, stops storage, archives its bind mounts, and restarts the live services even if archiving fails.
3. The script restores into a new directory and starts separate Mongo, Redis, Postgres, MinIO, etcd, Milvus and Neo4j containers. It publishes no ports and starts no application workers. Do not connect this network to the live application. Startup alone is **not** a successful recovery.
4. Run `python3 scripts/ops/verify_recovery.py --backup /data/semibrain/backups/<new-name>`. This compares authoritative data fingerprints, authenticates to Redis, verifies object content hashes and private-document access denial, recreates one representative document's vector projection from restored text, runs actual retrieval, and rebuilds the full graph topology. It records the tested scope and stops the rehearsal containers in a `finally` block. It retains the archive and restored files for operator inspection.
5. Check live health endpoints, the login page and a historical answer after maintenance. Record downtime separately from restore/verification duration. Review `verified.json`; do not claim complete vector re-embedding when only the representative projection was rebuilt. The cold snapshot restores the remaining vector data intact.

Application and storage images are pinned to the original digests. No application schema migration is executed by the storage restore. Rollback of an application release remains independent: restore the prior image/configuration references while preserving compatible data. An actual disaster restore requires explicit selection of the recovery point, restoration into a new location, verification, and an operator-approved cutover; these scripts deliberately do not overwrite live data or redirect traffic.

Limits: this is a separate Docker environment on the same host, not a second-host outage rehearsal; downloaded files cannot be revoked retrospectively; external model/search providers and Langfuse are not included in the backup; queues and transient authorization entries can expire normally after restoration. Local acceptance evidence must state these limits and whether an off-host copy exists.
